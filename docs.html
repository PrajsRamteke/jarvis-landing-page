Overview

Jarvis is a terminal-native AI coding agent — the Harness Agent that lives in your terminal. Talk to it, and it reads/writes files, runs shell commands, searches code, manages git, controls macOS apps, OCRs images, browses the web, and gets work done right where your code lives.

Install

One-command install (recommended)

curl -fsSL https://raw.githubusercontent.com/PrajsRamteke/harness-agent/main/scripts/install | bash
source ~/.zshrc

After install, open a new terminal, go to any project, and run jarvis.

Troubleshooting: If jarvis: command not found, add ~/.local/bin to your PATH: export PATH="$HOME/.local/bin:$PATH"

Development setup

git clone https://github.com/PrajsRamteke/harness-agent.git
cd harness-agent
python3 -m venv .venv
source .venv/bin/activate
pip install -e .
jarvis --help

Run the agent

jarvis                     # TUI mode (default)
python agent.py            # same as jarvis
python agent.py --legacy   # Rich REPL mode

Context Tools

The connected context pack replaces 5-20 separate file reads with a single call.

resolve_context

Give it a task description and get all related files — targets, imports, importers, tests, types, configs.

resolve_context(task="Fix login bug in JWT token refresh")
# Returns: jwt.py, auth.py, middleware.py, test_auth.py,
#          types.py, config.py — all in one shot

read_bundle

Batch-read 2-20 paths with parallel I/O and budget-aware output capping.

read_bundle(["src/auth.py", "src/middleware.py", "src/types.py"])

Tool Repair

A 14-stage auto-repair pipeline that validates and fixes model-generated tool inputs before execution. When the LLM sends malformed arguments — wrong types, extra fields, stringified JSON, wrong parameter names — the repair layer silently corrects them so you never see the error.

Each fixer is idempotent: correct inputs pass through with zero changes and no log entries. The UI shows a ⚒ indicator when repairs were applied.
# Stage Problem Fix Example
01 Parse stringified args Model sends a JSON string instead of a dict Parse string → dict "{"path":"x.py"}" → {"path":"x.py"}
02 Unwrap envelopes Args wrapped in an extra key like arguments, input, params Remove wrapper envelope {"arguments":{...}} → inner dict
03 Fix field aliases Wrong parameter name used (e.g. file_path instead of path) Rename to schema name file_path → path, old → old_str, query → pattern
04 Strip null values null sent for optional fields Remove null entries {"path":"x.py","limit":null} → {"path":"x.py"}
05 Strip extra fields Fields not in the tool's input schema Remove unknown keys {"path":"x.py","color":"red"} → {"path":"x.py"}
06 Parse stringified arrays Array sent as a JSON string Parse string → array "['a','b']" → ["a","b"]
07 Parse stringified objects Object sent as a JSON string Parse string → object "{...}" → {...}
08 Fix wrong containers Single value wrapped in array, or array expected but object sent Unwrap/wrap correctly [{...}] → {...}
09 Clean paths File path wrapped in array or has whitespace Unwrap and trim ["path"] → "path"
10 Fix string numbers Number sent as string Coerce to number "10" → 10
11 Fix boolean strings Boolean sent as string Coerce to boolean "true" → True
12 Coerce to string Array or object sent where string expected Join or serialize ["a","b"] → "a\nb"
13 Fix markdown paths Path wrapped in markdown link syntax Extract plain path [file.md](/path/file.md) → file.md
14 Repair nested arrays Array of objects where each object has issues (e.g. multi_edit.edits) Run stages 1-13 per item Fixes multi_edit.edits and ask_user_question.questions

The repair pipeline runs before any tool executes. It checks every argument against the tool's declared JSON schema and applies only the fixers needed — most calls pass through with zero changes. The UI shows a ⚒ indicator in the tool output line when a repair was applied, so you know the model had a formatting issue that was corrected silently.

Agents

Agents are reusable markdown files with YAML frontmatter that inject a system-prompt addon when activated. Think of them as specialized personas — a code reviewer, a security auditor, a technical writer — that you can switch between with a single command.

Anatomy of an agent

# .harness/agents/reviewer.md
---
name: reviewer              # lowercase-kebab, must match filename
description: Code review specialist — thorough, security-aware
icon: "🔍"                  # single emoji (optional)
color: "#58a6ff"            # hex color for status bar indicator (optional)
model: "claude-sonnet-4"   # pin a specific model (optional)
---

You are a code review specialist. Focus on:
1. Security vulnerabilities (injection, XSS, auth bypass)
2. Performance bottlenecks (N+1 queries, memory leaks)
3. Edge cases (empty states, concurrent access)
4. Code style & maintainability

Always provide specific line-level feedback with code suggestions.

How agents work

  1. Activation: Run /agent reviewer or press Tab to cycle through discovered agents
  2. Injection: The agent's body markdown is appended to the system prompt for every turn while active
  3. Persistence: The active agent name is saved to settings.json and restored on next launch
  4. Deactivation: Run /agent off to return to the default behavior

All agent commands

/agent <name> Activate an agent by name (e.g. /agent reviewer)
/agent new <name> Scaffold a new agent file with template frontmatter

/agent delete <name> Delete an agent file

Export / Import — one-key press

In the agent picker:

  • Press e to export the selected project agent → global scope (.harness/agents/ → ~/.harness/agents/)

Skills

Skills are instruction packs (SKILL.md files) that the LLM automatically loads when it detects the task matches the skill's description. Unlike agents (which you manually activate), skills are auto-invoked — the model decides when to load them based on relevance.

Anatomy of a skill

# .harness/skills/security-review/SKILL.md
---
name: security-review            # must match directory name
description: Audit code for OWASP Top 10 vulnerabilities, injected dependencies,
             and hardcoded secrets. Use whenever you see auth code, database
             queries, or user input handling.
compatibility: "Anthropic, OpenRouter, OpenCode"
---

## Security Review Checklist

1. Check for injection — raw string interpolation in queries
2. Check for XSS — unescaped user input rendered in templates
3. Check for hardcoded secrets — API keys, tokens, passwords
4. Check authentication — weak password rules, missing MFA
5. Check authorization — missing role checks, IDOR patterns
6. Check dependencies — known vulnerable package versions
7. Check output encoding — Content-Type headers, CSP policies

How skills work

  1. Discovery: On startup, Jarvis scans all skill directories and indexes the description field from each SKILL.md
  2. Auto-invocation: Each turn, the LLM evaluates which skill descriptions match the current task context
  3. Loading: Matching skills are loaded via skill_load<name> and their body is added to the system prompt
  4. Multiple skills: Several skills can be active at once — the LLM loads all that match

Skill commands

Command Action
/skill or /skills Open skill browser modal — read-only, lists all discovered skills with descriptions
/skills global on Enable global skill discovery (scans other tool directories)
/skills global off Disable global skill discovery

Export/import in the skill browser: Press e to export a project skill to global scope, or i to import a global skill into your project.

Skill directories

Skills must be in a directory named after the skill, containing a SKILL.md file:

  • .harness/skills/<name>/SKILL.md (primary project location)
  • .skills/<name>/SKILL.md (legacy)
  • .opencode/skills/<name>/SKILL.md (OpenCode compatibility)
  • .claude/skills/<name>/SKILL.md (Claude Code compatibility)

When global scope is on (/skills global on), skills from these sources are also discoverable:

Source tool Path scanned

Important: The directory name must equal the name: field in frontmatter. Jarvis uses the directory name to locate and load the skill. Skills with mismatched names will not be discovered.

Custom Commands

User-defined prompt templates that you trigger with /<name>. Drop a markdown file in .harness/commands/ and it becomes a first-class slash command — just like the built-in ones.

Example

# .harness/commands/pr-description.md
---
name: pr-description
description: Generate a PR description from the current diff
argument-hint: "[focus area]"
---
Write a structured PR description with:
- Summary (one paragraph)
- Changes (key list)
- Testing (how to verify)
- Related issues

$ARGUMENTS

Template placeholders

Placeholder Substituted with
$ARGUMENTS Everything typed after /<name>
$1 through $9 Positional arguments (parsed with shlex — respects quoting)

If arguments are provided but no placeholder exists in the template, they're appended on a new line.

MCP Support

Jarvis supports the Model Context Protocol (MCP) — an open standard for connecting external tools and data sources to the LLM. MCP servers add dynamically discovered tools that the agent can invoke, expanding its capabilities beyond the built-in tool set.

Quick start — /mcp modal

Type /mcp in the TUI to open the MCP server manager. From here you can:

  • View connected servers — see all active MCP servers and their available tools
  • Connect — load servers defined in the project's .mcp.json
  • Disconnect — stop a specific server
  • Toggle global scope — press g to load servers from other tools
  • Refresh — re-read config files for newly added servers

Project scope (default)

By default, only the project's .mcp.json is loaded. This keeps MCP servers scoped to the project that needs them — perfect for per-project database tools, API connectors, or build tools.

{
  "mcpServers": {
    "my-db": {
      "command": "node",
      "args": ["path/to/mcp-server.js"],
      "env": { "DB_URL": "..." }
    }
  }
}

Global scope — press g

Press g in the /mcp modal to toggle global scope. When enabled, Jarvis reads MCP configurations from other AI coding tools on your machine — so you don't need to duplicate server configs.

Global MCP — import from Claude Code, OpenCode, Cursor

Source tool Config file read
Claude Code ~/.claude/settings.json (mcpServers key)
OpenCode ~/.config/opencode/mcp.json
Cursor ~/.cursor/mcp.json
Legacy Claude ~/.config/claude/mcp.json
One press to rule them all: Press g in the /mcp modal to instantly import all MCP servers from every supported tool. No manual copying, no config file hunting.

How MCP tools work

  1. Connection: Jarvis starts each MCP server as a subprocess and communicates via JSON-RPC over stdio
  2. Tool discovery: The server advertises its available tools (name, schema, description)
  3. Registration: Discovered tools are added to MCP_TOOLS group and become available to the agent
  4. Invocation: When the LLM selects an MCP tool, Jarvis calls it through the connected server and returns the result
  5. Cleanup: When the session ends or the server is disconnected, tools are removed from the registry
Privacy: Global MCP servers from ~/.cursor, ~/.claude, and ~/.config/opencode are only loaded when you explicitly toggle global scope on. They are never read without your permission.

No Project Jail

Unlike most AI coding agents that lock you inside the current working directory, Jarvis has no project jail. It can read, write, edit, and search files anywhere on your machine — the project root is just a default starting point, not a cage.

Full filesystem access means you can inspect system configs, edit dotfiles, search sibling projects, and read logs without leaving the chat.

Tools with outside-project access

Tool Flag to use Example
read_file force=true Read ~/.ssh/config, /etc/hosts, log files
write_file allow_outside_project=true Write to ~/dotfiles/, /tmp/, ~/Desktop/
edit_file allow_outside_project=true Patch a config file in ~/.config/
multi_edit allow_outside_project=true Edit multiple files in ~/projects/
list_dir allow_outside_project=true List /Applications/, ~/Downloads/
search_code allow_outside_project=true Search ~/Documents/ for a string
glob_files allow_outside_project=true Find all *.log in ~/Library/Logs/
read_document force=true Read PDFs, images, spreadsheets anywhere
fast_find No flag needed Spotlight-search across entire Mac in milliseconds

Real-world use cases

  • System configs: Read ~/.zshrc, ~/.ssh/config, /etc/hosts, /etc/profile
  • Logs: Inspect /var/log/, ~/Library/Logs/, Docker container logs
  • Dotfiles: Edit your ~/.gitconfig, ~/.tmux.conf, ~/.config/nvim/
  • Sibling projects: Search code in ../other-project/, copy files between projects
  • Downloads & Desktop: Find files in ~/Downloads/, process screenshots on ~/Desktop/
  • Installation dirs: Inspect /usr/local/, /opt/homebrew/, pip/brew install receipts
Safety first: Outside-project access requires explicit opt-in per call with force=true or allow_outside_project=true. Jarvis never reads outside the project without being told to. This prevents accidental modification of system files while still giving you full power when you need it.

FAQ

▸ How do I update Jarvis?

Run /upgrade in the TUI. It pulls the latest version from GitHub.

▸ Can I use Jarvis offline?

Core file/git/shell tools work offline. The LLM needs an internet connection for API calls.

▸ Does it work on Linux or Windows?

Core agent works on any platform. macOS control tools are macOS-only.

▸ How do I switch providers?

Type /provider in the TUI or set HARNESS_PROVIDER env var.

▸ How is my data handled?

All data is local — SQLite sessions, JSON memory. No telemetry sent anywhere.

Troubleshooting

Jarvis won't start

brew install python@3.11

"command not found: jarvis"

export PATH="$HOME/.local/bin:$PATH"

Authentication issues

  • Check ANTHROPIC_API_KEY: echo $ANTHROPIC_API_KEY

macOS accessibility denied

  1. System Settings → Privacy → Accessibility
  2. Add your terminal app
  3. Restart terminal
